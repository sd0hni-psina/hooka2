# PLAN.md: аудит проекта и чек-лист исправлений

Дата: 2026-09-21. Версия ядра контракта на момент аудита: v15. Ветка: `main`, коммит `750c4ae`.

Аудит ничего не менял в коде и в `tech.md`. Правки контракта ниже оформлены как `CONTRACT GAP` и ждут решения владельца.

## 1. Вердикт

Слои разведены честно, домен чистый, планировщик идемпотентен по состоянию, гонка подтверждения закрыта условием в `WHERE`, время идёт от `serverNow()`, `any` и литералов цвета в клиенте нет. Все локальные гейты зелёные.

Проблемы лежат там, где тесты не смотрели:

1. Код входа подбирается за секунды: лимит привязан к `device_id`, а его выбирает клиент.
2. Пуши продолжают идти по завершённому кальяну и по уже подтверждённой задаче. Это прямо противоречит разделам 7 и 10 `tech.md`.
3. Повтор старта кальяна с тем же `Idempotency-Key` в момент гонки отдаёт `409` вместо `200`, а в другом варианте `500`.
4. Клиент не замечает мёртвый сокет и возврат из фона: мастер может читать устаревший зал и считать его живым.
5. Релиз упирается в операционные хвосты владельца: результат CI на GitHub мне неизвестен, в `eas.json` стоит `api.example.com`, для Android push нет FCM-конфигурации.

Серверные пункты 1-3 живут и в `~/Projects/hooka2-v2`. `REVIEW.md` форка называет серверную половину не требующей переделки, а сервер там тот же по коду (`diff -rq server` отличается только каталогом `testdata`). Исправлять сервер нужно здесь и переносить в форк.

## 4. Критично

### [x] A1. Код входа подбирается за секунды

- **Найдено** [воспроизведено]: лимит считается только по `device_id` (`internal/staff/service.go:123-133`, `repository.go:210`). `device_id` присылает клиент, любая строка от 8 до 128 символов. Тест: 40 попыток с разными `device_id` дали 39 раз `404 invalid_join_code`, ни одного `429`, а 40-я, с верным кодом, вернула `200` и сессию. Контроль: с одного `device_id` лимит срабатывает после пятой попытки. Пространство кодов 10 000, IP-лимита и общего лимита нет. `tech.md` раздел 7 называет эти три меры защитой от подбора, но первая из них обходится одним заголовком.
- **Приоритет**: критично. Посторонний получает сессию мастера: видит весь зал, стартует и завершает кальяны.
- **Исправить**: добавить лимит по IP и общий бюджет неверных попыток на весь сервис. Учесть NAT: за одним wifi заведения сидят все мастера, лимит IP должен быть мягче лимита устройства. За Caddy настоящий адрес приходит в `X-Forwarded-For`, доверять ему можно только от Caddy (api наружу не опубликован, `deploy/docker-compose.prod.yml`). Альтернатива или дополнение: код из 6 цифр. Выбор за владельцем. Нужен `CONTRACT GAP` G1 ниже и миграция `0004`.
- **Критерий приёмки и тест**: в `apitest` серия из N попыток с разными `device_id` и одного IP упирается в `429` с `retry_after_sec`. Контроль: попытки с разных IP не блокируют друг друга. Тест на границе окон уже есть в `domain/join_test.go`, расширить его.

### [x] A2. Пуши идут по завершённому кальяну

- **Найдено** [воспроизведено]: `internal/push/queue.go:48-58` выбирает события `state = 'due'` и не смотрит на `hookahs.state`. `tech.md` раздел 7: события в `due` остаются для истории, «очередь пушей по ним останавливается». Тест: кальян с `due`-событием завершён через API, следующий тик очереди поставил 4 пуша. Типичный сценарий: гость ушёл, жёлтый стол закрыли, телефоны всех мастеров получили ещё до двух повторов (сколько именно, зависит от оставшихся попыток).
- **Приоритет**: критично. Нарушение явного правила контракта в обычном рабочем потоке.
- **Исправить**: добавить `and h.state <> 'finished'` в запрос кандидатов в `queue.go`. Контракт менять не нужно.
- **Тест**: завершить кальян с событием в `due`, прогнать `queue.Tick` дважды, ожидать `Queued == 0` и ноль новых строк `push_deliveries`. Тест из раздела 17, слайс 3, «пуши по ним не идут».

### [x] A3. Воркер шлёт пуши по подтверждённой и завершённой задаче

- **Найдено** [воспроизведено]: `internal/push/worker.go:60-70` берёт все строки `queued` и не проверяет состояние события. Тест: очередь поставила 4 пуша, задачу подтвердили, `RunOnce` отправил все 4. Транспортные повторы через 5, 15, 45 секунд по коду ведут себя так же (`retry_at` не связан с состоянием события), отдельно их не воспроизводил. `tech.md` раздел 10: подтверждение и `missed` останавливают повторы, мастеру, подтвердившему задачу, повторы не идут.
- **Приоритет**: критично. Пуш «Стряхните угли» приходит по уже сделанной задаче.
- **Исправить**: в запрос воркера добавить `e.state = 'due' and h.state <> 'finished'`. Строки закрытых событий нужно перевести в конечный статус, иначе они вечно висят в `queued` и раздувают частичный индекс. Подходящего статуса в схеме нет (`queued|sent|failed|invalid_token`), поэтому `CONTRACT GAP` G2: статус `cancelled` и миграция `0004`. Без него можно временно писать `failed` с `error = 'event closed'`, но это смешивает отказ транспорта с отменой.
- **Тест**: очередь, подтверждение, `worker.RunOnce`: `fake.Sent()` пуст, строки `cancelled`. Повторить для транспортного повтора и для завершённого кальяна.

### [x] A4. Повтор старта с тем же ключом в гонке: `409` и `500`

- **Найдено** [воспроизведено]: `internal/hookah/service.go:219-238` и `repository.go:91-105`. Два сценария.
  1. Один ключ, один стол, 8 параллельных запросов: получили `200` от 1 до 8 раз, остальные `409 table_occupied`. По `tech.md` 19.8 повтор с тем же ключом обязан вернуть `200` и тот же кальян. Причина: нарушение индекса стола срабатывает раньше индекса ключа.
  2. Один ключ, два стола, 16 параллельных запросов: 4 и более ответа `500` с `current transaction is aborted (SQLSTATE 25P02)`. Причина: после нарушения уникального индекса ветка `repeated` делает ещё запросы в той же транзакции, а Postgres такую транзакцию считает прерванной.
  Существующий тест гонки использует разные ключи на каждый запрос, поэтому этих случаев не ловит. Последовательный повтор работает.
- **Приоритет**: критично. Идемпотентность старта нужна именно для повторов вокруг сбоев сети, а `500` на ней ломает контракт `internal` не по делу.
- **Исправить**: заменить `insert ... returning id` на `insert ... on conflict do nothing returning id`. Нет строки: искать кальян по `(venue_id, idempotency_key)`, нашли значит вернуть его как `200`, не нашли значит `table_occupied`. Транзакция не прерывается, оба индекса обрабатываются одним путём. Контракт не меняется.
- **Тест**: 8 параллельных запросов с одним ключом на один стол: все `200`, один `hookah.id`, одна строка в `hookahs`, 7 событий. 16 параллельных запросов с одним ключом на два стола: ни одного `500`, одна строка.

### [x] A5. Клиент не замечает мёртвый сокет и возврат из фона

- **Найдено** [по коду]: в `src/ws/client.ts` нет проверки, что сервер отвечает: клиент шлёт `ping` раз в 20 секунд, но не ждёт `pong`. Обрыв без FIN (смена сети, блокировка телефона, потеря сигнала) может не вызвать `onclose`: тогда статус остаётся `online`, схема выглядит живой и молчит. `grep` по `src` и `app` не нашёл ни `AppState`, ни `NetInfo`. `onclose` не читает код закрытия: заблокированный мастер (1008) и переполнение буфера (1011) обрабатываются одинаково, `attempt` сбрасывается в 0 при каждом `onopen`, так что цикл 1011 идёт без нарастающей паузы.
- **Приоритет**: критично. Продукт продаёт доверие к таймерам, а мастер, вернувшийся из фона, видит зал двухминутной давности без единого признака этого.
- **Исправить**:
  1. Watchdog в `WsClient`: запоминать время последнего кадра, при тишине дольше 45 секунд закрывать сокет и переподключаться. Сервер отвечает `pong` на каждый `ping`, поэтому живое соединение молчать не может.
  2. `AppState` в `useHallConnection.ts`: при возврате в `active` сразу переподключаться без ожидания бэкоффа и слать `subscribe`, чтобы взять снапшот.
  3. Разбор кода закрытия: 1008 останавливает переподключение и запускает `refreshMe` (сессия отозвана), 1011 переподключается с растущей паузой, `attempt` сбрасывается после первого снапшота, а не на `onopen`.
  Контракт менять не нужно (раздел 9 не запрещает клиентскую проверку живости).
- **Тест**: расширить `src/ws/__tests__/client.test.ts` с fake-таймерами: тишина 45 секунд закрывает и переподключает; возврат из фона переподключает сразу; код 1008 не запускает цикл переподключений. Ручная проверка: заблокировать телефон на 2 минуты, разблокировать, засечь время до свежего снапшота.
- **Заметка**: `REVIEW.md` форка описывает возврат из фона. Проверки живости сокета там не описано, код форка не смотрел. Можно перенести, а не писать заново.

### [x] B4. Выход не закрывает открытый WS

- **Найдено** [по коду]: `Logout` (`internal/staff/service.go:231`) только помечает сессию `revoked_at`. Закрытие сокетов (`hub.CloseStaff`) вызывается лишь при блокировке (`service.go:319`). Токен проверяется один раз при апгрейде, поэтому сокет вышедшего устройства продолжает получать события зала, пока живо соединение.
- **Приоритет**: желательно. Телефон, отданный другому человеку, или украденный токен.
- **Исправить**: `CONTRACT GAP` G4. Метод `Hub.CloseSession(venueID, sessionID)`, вызов из `Logout`, закрытие кодом 1008.
- **Тест**: после `logout` сокет этой сессии закрыт кодом 1008, сокеты других сессий того же мастера живы.

### [x] B5. Воркер держит транзакцию во время HTTP-вызова в Expo, у пула нет явного лимита

- **Найдено** [по коду]: `internal/push/worker.go:59-130` держит транзакцию с блокировками строк на всё время `sender.Send` (таймаут до 10 секунд, до 100 сообщений). `store.NewPool` не задаёт `MaxConns`, значит по умолчанию `max(4, число ядер)`. На малом VPS медленный Expo плюс всплеск запросов (каждый запрос ещё делает `CheckSession`) могут выбрать пул.
- **Приоритет**: желательно.
- **Исправить**: сначала явно задать `MaxConns` в `store/pool.go`, чтобы предел был осознанным. Если нагрузка вырастет: забирать строки короткой транзакцией, слать вне транзакции, отмечать результат второй короткой (нужен промежуточный статус `sending`, это `CONTRACT GAP`).

### [x] B6. Неудачный refresh с ответом 5xx разлогинивает мастера

- **Найдено** [по коду]: `src/store/auth.ts:110-113` очищает сессию на любую `ApiError`. Ответ `502` от Caddy во время выкатки (деплой идёт на каждый мёрдж в `main`) или `500` тоже становятся `ApiError`. Мастер посреди смены попадает на `join`. Сетевая ошибка (`NetworkError`) сессию не трогает, корректно.

## 6. Что проверено и в порядке

- Границы слоёв: в `domain` нет `pgx`, `net/http` и `time.Now`, SQL в хендлерах нет, ветвлений по ролям в репозиториях нет.
- Планировщик: каждый из трёх запросов меняет состояние, повторный тик находит ноль строк, выборка событий с `for update skip locked` захватывает и строку кальяна, поэтому тик не пересекается с `finish` (по коду, гонку тика и `finish` не воспроизводил). Очередь пушей выбирает кандидатов по состоянию, а не по результату `MarkDue`, поэтому падение между коммитами пуш не теряет.
- Гонка подтверждения: условный `update ... where state in ('due','pending') and confirmed_at is null`, `due_at` не двигается, проигравший получает `200`.
- Перенос сохраняет `started_at`, `expires_at` и все `due_at`. План берётся из `plan_snapshot`.
- JWT: алгоритм закреплён на HS256, `exp` обязателен, время передаётся аргументом, сессия и блокировка проверяются на каждом запросе.
- Блокировка мастера: сессии отзываются в транзакции, сокеты закрываются кодом 1008.
- Seq в хабе выдаётся и рассылается под одним локом, доставка не блокирует, переполнение закрывает соединение.
- Клиент: нет `any`, нет `Date.now()` вне `clock.ts`, нет литералов цвета, единственный интерпретатор WS-событий, снапшот всегда заменяет стор.
- Миграции 0001-0003 применяются на чистой БД и повторно, `cmd/seed` отказывается работать при `APP_ENV=prod`. Prod-образ собирается на distroless под `nonroot`, Postgres и api наружу не опубликованы.
- Тесты: property-тесты `rapid` на `MaterializePlan`, `TableStatus`, лимит входа и планировку; Go и Jest читают одни фикстуры `/contracts/fixtures`; есть тесты идемпотентности, гонки подтверждений, ошибок Expo.
