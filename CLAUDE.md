# CLAUDE.md — правила разработки

Проект: Кальянный таймер. Разработчик один, ролевых файлов нет. Этот файл читается в каждой сессии и действует на весь код, тесты, коммиты и документы.

## 1. Источник истины

`tech.md` в корне репозитория — единственный источник истины по контрактам: схема БД, формат эндпоинтов, payload WS-событий, общие типы, перечень UI-примитивов, структура папок, конвенции, критерии приёмки слайсов.

Перед задачей прочитай `tech.md` целиком и подчиняйся ему дословно. Расхождение кода и `tech.md` — баг в коде, пока владелец репозитория не решил обратное.

Проверь версию ядра в начале `tech.md`. Пишешь код против той версии, которая в файле сейчас, не против того, что помнишь из прошлой сессии.

## 2. CONTRACT GAP

Тебе не хватает поля, типа, эндпоинта, события, таблицы или кода ошибки. **Стоп.** Код с выдуманным контрактом не пиши.

Выдай блок и жди решения:

```
CONTRACT GAP
Нужно: service_events.snoozed_until timestamptz
Зачем: слайс 4, мастер откладывает задачу на 5 минут, без поля состояние живёт только в памяти клиента
Предлагаемая форма: nullable timestamptz, миграция 0007, поле в ServiceEvent, новое WS-событие service.snoozed {event_id, snoozed_until}
Блокирует: экран задач, кнопка «Отложить»
Обходной путь на время ожидания: кнопка скрыта за флагом, остальная часть слайса идёт без неё
```

Дальше: владелец аппендит контракт в `tech.md`, бампает версию ядра, добавляет строку changelog. Только после этого пишешь код.

Три типичных случая, где сессия срывается в выдумывание, и правильное поведение:

- Нужного поля нет в схеме → `CONTRACT GAP`, не `ALTER TABLE` по ходу.
- Нужного кода ошибки нет в таблице раздела 8 → `CONTRACT GAP`, не строка-литерал в ответе.
- Нужного примитива нет в `src/ui` → добавляешь примитив, записываешь в таблицу раздела 12, бампаешь версию. Своя вёрстка кнопки внутри фичи запрещена.

## 3. Один слайс, одна задача

Дорожная карта в разделе 17 `tech.md`. Слайс не начинается, пока предыдущий не в main. Слайс 0 не считается пройденным, пока чек-лист «скелет готов» не зелёный по каждому пункту.

Внутри слайса делай одну задачу за раз и отдавай сфокусированный дифф. Не выкатывай весь слайс одним куском: его невозможно ни прочитать, ни проверить.

Порядок внутри задачи фиксированный:

1. Миграция, если задача её требует.
2. Чистая доменная логика в `internal/domain` или `src/domain` плюс её тесты.
3. Репозиторий, сервис, хендлер.
4. Интеграционные и API-тесты из критериев приёмки.
5. Клиент: типы, стор, экран.
6. Ручная проверка на двух устройствах.

Не начинай с экрана. UI поверх непроверенной доменной логики прячет баги в таймерах, а таймеры здесь и есть продукт.

## 4. Эталон

Первая вертикаль слайса 0 (`GET /me`: репозиторий, сервис, хендлер, регистрация роута, тип на клиенте, экран) — шаблон, не пример. Каждый следующий слайс повторяет её раскладку файлов и имён. Сверяйся с ней, свою раскладку не изобретай.

## 5. Границы слоёв

```
handler → service → repository
              ↓
           domain
```

- `handler` парсит вход, зовёт сервис, мапит доменные ошибки в коды раздела 8. SQL и бизнес-правил в нём нет.
- `service` держит сценарий и транзакцию, публикует WS-события, ставит пуши.
- `repository` — только SQL и маппинг. Ветвлений по ролям и бизнес-правил в нём нет.
- `domain` — чистые функции. Импорты `pgx`, `net/http`, `time.Now()` запрещены, время приходит аргументом.

Нарушение границы — переписать, не обойти.

## 6. Правила, которые ломаются чаще всего

**Время.** Сервер — единственный источник времени. На клиенте только `serverNow()` из `src/ws/clock.ts`. `Date.now()` в отсчётах и в вычислении статуса запрещён.

**Подтверждение не сдвигает таймер.** `due_at` будущих событий и `expires_at` кальяна неизменны после старта. Подтверждение пишет `confirmed_at` и `confirmed_by`, больше ничего.

**Перенос сохраняет время.** Меняются `table_id` и `hall_id`, пишется строка в `hookah_transfers`. `started_at`, `expires_at`, все `due_at` остаются на месте.

**План фиксируется снапшотом.** Кальян живёт по `plan_snapshot`, взятому при старте. Смена настроек заведения не трогает живые кальяны.

**Идемпотентность.** Каждый запрос планировщика идемпотентен через условие на состояние. Каждая мутация с `Idempotency-Key` при повторе отдаёт тот же объект. Тест на двойной прогон обязателен, иначе получишь два кальяна на столе и двойные пуши.

**Гонки.** Обновление состояния идёт с условием в `WHERE` (`state = 'due' and confirmed_at is null`), не через «прочитал, проверил, записал». Два мастера жмут подтверждение одновременно — оба видят успех, в БД один `confirmed_by`.

**Реконнект.** После обрыва клиент всегда заменяет стор снапшотом, а не мержит. Разрыв `seq` — тоже причина взять снапшот.

**Статус стола.** Одна функция, две реализации (`domain.TableStatus` и `src/domain/status.ts`), одна фикстура `/contracts/fixtures/status_cases.json`. Меняешь правило — правишь фикстуру, обе реализации и `tech.md`.

## 7. Тесты

Тест выводится из критериев приёмки задачи, не из реализации. Тест кодирует контракт.

Запрещённый порядок: написал код, потом написал тест, который подтверждает, что код делает то, что делает. Такие тесты зелёные и не проверяют ничего, вместе с багами.

Обязательный минимум на слайс:

- контрактный тест на стыке против фикстуры из `/contracts/fixtures`;
- тест идемпотентности на каждый запрос планировщика и каждую мутацию с `Idempotency-Key`;
- путь ошибки: занятый стол, завершённый кальян, гонка подтверждений, обрыв WS, ошибка Expo, невалидный токен устройства;
- property-based (`rapid`) на чистой логике: `MaterializePlan`, `TableStatus`;
- тест редьюсера WS-событий на последовательности сообщений.

Тесты пишешь в том же PR. PR без тестов не мёрджится.

## 8. Коммиты

Английский. Формат фиксированный, всегда: `type(scope): summary`.

- `type`: `feat|fix|test|refactor|chore|docs`.
- `scope`: домен или пакет (`hookah`, `layout`, `ws`, `push`, `ui`, `ci`).
- `summary`: императив, строчная буква, без точки, до 50 символов, по делу.
- Тело только чтобы объяснить **почему**.

Коммить самому по ходу работы, маленькими логическими коммитами после каждого осмысленного шага. Не сваливай всё одним коммитом в конце. Каждый коммит по возможности проходит тайпчек.

```
feat(hookah): materialize service events on start
fix(ws): resend snapshot after seq gap
test(scheduler): cover double tick idempotency
```

Ветка на слайс: `slice/03-hookah-lifecycle`. PR в main на слайс, тело короткое: что делает слайс, какие контракты затрагивает, чем покрыт тестами, что проверил руками.

## 9. Self-review перед мёрджем

Пройди по пунктам механически, не на глаз:

- Нет выдуманных типов, полей и кодов ошибок. Всё из `tech.md`.
- Границы слоёв целы: в `domain` нет БД и HTTP, в `repository` нет правил.
- UI собран из примитивов `src/ui`, литералов цвета и отступов в компонентах нет.
- Тесты проверяют контракт из критериев приёмки, а не реализацию.
- Для каждого запроса планировщика и каждой идемпотентной мутации есть тест двойного прогона.
- На стыке слайса есть контрактный тест против фикстуры.
- Отсчёты идут от `serverNow()`, `Date.now()` в них нет.
- Миграция применяется на чистой БД и на БД с сидом, применённые файлы не тронуты.
- `golangci-lint`, `go vet`, `tsc --noEmit`, `eslint` чистые. `go test ./... -race` и `jest` зелёные.
- Ручной чек-лист слайса пройден на двух устройствах, синхронизацию видел глазами.
- Контракт изменился → `tech.md` обновлён, версия ядра бампнута, changelog дописан.

## 10. Запреты

- Не выдумывай контракт. Не хватает — `CONTRACT GAP`.
- Не правь применённую миграцию. Новое изменение — новый файл.
- Не добавляй зависимость без записи в раздел 3 `tech.md` и бампа версии.
- Не рефакторь код чужого слайса по ходу своей задачи. Заметил проблему — запиши, вынеси отдельной задачей.
- Не заводи слой абстракции «на будущее». Интерфейс появляется, когда есть вторая реализация или фейк для тестов.
- Не пиши в `main` напрямую.
- Не ставь `any` в TypeScript и не глотай ошибку в Go пустым `_`.
- Не трогай реальные ключи Expo в разработке. Провайдер пушей в dev и тестах — `fake`.
- Не используй локальные запланированные уведомления как замену серверным пушам. Причина в разделе 10 `tech.md`.

## 11. Неопределённость

Требование неоднозначно, два решения выглядят равными, или задача выходит за границы v1 из раздела 1 `tech.md` — остановись и спроси. Не угадывай и не расширяй скоуп молча. Одна строка вопроса дешевле слайса, который придётся переделать.

## 12. Проза

Документы, описания PR, комментарии, пользовательские строки: активный залог, императив, конкретика вместо общих фраз. Без филлеров, без em-dash, без эмодзи. Комментарий объясняет **почему**, а не пересказывает код. Закомментированный код в PR не оставляй.

Код, коммиты, PR и комментарии — английский. Пользовательские строки — русский, в `src/i18n/ru.ts`.
